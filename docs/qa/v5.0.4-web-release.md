# v5.0.4 — Pilot readback stability

## Scope

- Tactical setup now recognizes its own setup screen when opening **Test Headphones · Pilot Readbacks**. The same headphone test, confirmation, and mute rules remain in force for Single and Tactical.
- Offline pilot PCM is assembled before input teardown completes. Each playback starts with a bounded 240 ms silent key-up and a 10 ms fade into speech, so the first spoken samples do not coincide with a phone output-route transition. The radio and D/F transmission begin at key-up; flight commands still execute independently of pilot audio.
- The controller workflow, aircraft physics, voices, selected WPM rates, manual controls, and PTT interruption semantics are unchanged.
- This is a browser-route mitigation, not a claim that a Pixel USB-C audio route has been certified. The microphone still closes and reopens between calls; the route transition may recur.

## Automated evidence

- 508 engine/web tests passed, including targeted PCM timing and cancellation tests.
- 12 real-browser headphone-consent flows passed for Single and Tactical, Normal and U/S, at desktop and phone-sized viewports.
- 48 Single/Tactical Normal/U/S exercise-and-review browser flows passed across desktop, tablet, 320–430 px portrait phone widths, and phone landscape; no horizontal overflow or dock-outside-viewport error was found.
- The Continuous Listening browser probe passed with packaged pilot PCM, a simulated microphone and scripted recognition. It confirmed the silent lead, speech after the lead, complete reply playback, no premature microphone acquisition, and PTT replacement without a stale completion callback.
- The mobile-sized browser audio probe passed at 390×844 and 393×873 with real packaged PCM, suspend/resume, cancellation, and manual controls. The installed WebKit runtime lacked Web Audio and is not counted as iPhone audio evidence.
- A separate offline PWA run cached all nine pilot-bank assets with verified hashes, played all four pilot voices offline, completed a control/reply sequence, and reloaded offline without fetching a remote asset.
- The existing browser upgrade check passed for a returning v4.4.0 service worker and required fresh headphone consent. It does **not** establish the exact v4.4.9.1 upgrade path.
- Web build, release-version alignment, and Android/Windows source-bundle hash verification passed. Native installers were not built or released.
- Training screen recordings were not re-rendered: they show the visually unchanged v5.0.3 interface, while their cache metadata is aligned to v5.0.4 so the optional guides remain available. The new headphone-route timing is covered by tests, not by those recordings.

## Remaining device checks

**NOT RUN:** real Pixel 9a with wired USB-C headphones, physical microphone capture, Android background/foreground transitions, iPhone Safari audio routing, and upgrade from an installed v4.4.9.1 PWA. These cannot be inferred from browser emulation or synthetic input. Netlify deployment is separate from this GitHub Pages release.

On the Pixel, wear USB-C headphones and use **Test Headphone Audio**. In an exercise, try **Report heading** and a turn first with PTT, then with Continuous Listening. Let each pilot reply finish, including the first word and callsign. Repeat with a quick controller interruption. If speech still clips, record which mode, browser/PWA, visible version, and whether the first or middle of the reply is lost. Stop using audible pilot replies if they affect control input; manual controls and muted captions remain available.
