# v5.0.3 — Continuous audio handoff

## Problem and evidence

The phone retest narrowed the fault: headphones confirmed, ordinary manual-control replies audible with voice off, but replies cutting out with Continuous Listening on. The manual TRANSMIT FOR D/F button is separately implemented as a silent four-second transmission plus a two-second bearing hold; that behaviour is unchanged.

Pre-v5 comparison: 68 assembled ordinary replies (17 intents, four voices) were byte-identical between 4.4.9.1 and initial v5. The audio recordings themselves were not the regression.

A repeatable browser probe exposed an input/output race in v5.0.2:

1. Recognition ended and queued a pilot reply for 300 ms later.
2. Continuous Listening restarted at 180 ms and requested microphone access again.
3. Pilot playback cancelled that pending capture. Its audio context closed, so the input-release barrier settled.
4. Pilot playback started at about 325 ms, but the cancelled microphone request did not resolve until about 526 ms. A live input stream therefore arrived during pilot playback before being immediately stopped.

The Windows browser reproduced this ordering, **not physical USB-C sound loss**. This is a confirmed handoff defect and a plausible cause of the phone symptom, not proof that all phone audio issues are resolved.

## Changes

- `offline-voice-engine.js`: input-release tracking now includes pending microphone acquisition. A cancelled late stream is stopped before release completes; context closures are also awaited.
- `radio-workspace.js`: exposes whether a ready, enabled pilot output has queued replies or reports.
- `voice-workspace.js`: automatic continuous startup waits while audible work is queued, including a readiness check that completes asynchronously. It retries if work is discarded, muted or unavailable. Explicit PTT still takes priority.
- No aircraft physics, commands, captions, DF timing, headphone consent, UI layout, voice clips or WPM settings changed.
- Native source version metadata is aligned for the existing release validator; **no Android or Windows package is built**.

## Verification

- Existing and new Node suites: **508 passed**, including randomized Single Normal/U/S exercises and Tactical fleet tests.
- Ten added regression tests cover pending microphone grant/rejection/closure, queued audible replies and report-only queues, unavailable/muted/discarded/inactive recovery, STOP, explicit PTT and readiness races. New tests failed on the previous implementation before their corresponding fixes.
- Real-browser `qa-continuous-audio-handoff.cjs`: packaged pilot worker/PCM and actual WebAudio input/output graph; synthetic silent microphone and scripted recognition. It records event timing and signal levels, not user microphone recordings.
- Continuous flow: no extra microphone acquisition before/during its reply; full PCM duration with signal in beginning, middle and end; stale recognition ignored.
- Separate manual-command-during-pending-input flow: a delayed microphone grant is stopped before the barrier settles and before pilot source start. No recognizer graph is created for the cancelled capture.
- Explicit PTT interrupts an old reply; the replacement plays once and completes.
- Broader `qa-mobile-pilot-audio.cjs`: Edge mobile-sized viewports exercise real offline voices, interruptions, cancellation, mute and manual controls. Installed WebKit lacks WebAudio and is **not** counted as an iPhone audio pass.
- Version alignment, web build and whitespace validation pass.

## Review and limits

Targeted reuse, code-quality and efficiency review completed. No behaviour-preserving simplification was needed. The short existing restart timer is retained because output availability has no reliable cross-platform change event; it is cleared by STOP, pilot playback and lifecycle cancellation. Coalescing browser permission prompts is a broader pre-existing concern, not part of this hotfix.

The prior tests covered context close but mocked microphone acquisition as immediate; the earlier browser audio test never opened an input graph. Those gaps allowed the handoff race to pass.

**Physical Pixel 9a with USB-C headphones still requires user verification.** Synthetic input and phone-sized desktop viewports cannot establish physical headphone routing, speech intelligibility or iPhone behaviour.
